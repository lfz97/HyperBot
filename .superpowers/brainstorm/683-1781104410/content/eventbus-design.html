方案 B：EventBus 详细设计

用 Go channel 彻底解耦业务逻辑和 TUI 渲染

核心思路

  ┌─────────────────────┐          ┌──────────────────────┐
  │  业务层 (handler/    │   emit   │  渲染层 (goroutine)    │
  │  session/ bootstrap) │ ──────→  │  消费 RenderEvent     │
  │                      │  channel │  QueueUpdateDraw → TUI │
  └─────────────────────┘          └──────────────────────┘

  业务层只管 emit 事件，不 import tview / tcell
  渲染层一个 goroutine 跑到底，收事件 → 调 TUI API

事件类型设计

// output/renderEvent.go

type EventType int
const (
    EvtMessageChunk    // 流式正文片段
    EvtReasoningStart   // 开始思考
    EvtReasoningChunk   // 思考内容
    EvtReasoningEnd     // 结束思考
    EvtToolCall         // 工具调用
    EvtToolResult       // 工具结果
    EvtUserInput        // 回显用户输入
    EvtError            // 错误信息
    EvtStatusUpdate     // 状态栏更新
    EvtSystemMsg        // 系统消息（新对话/退出/刷新等）
    EvtSummary          // 摘要生成通知
    EvtShutdown         // 关闭渲染 goroutine
)

type RenderEvent struct {
    Type    EventType
    Content string
    Args    string // 工具参数（EvtToolCall 时用）
    Style   string // 颜色风格（EvtStatusUpdate/EvtSystemMsg 时用）
    // 不包含任何 tview/tcell 类型
}

EventBus 结构

// output/eventBus.go

type EventBus struct {
    ch     chan RenderEvent
    done   chan struct{}
    writer io.Writer  // CLI 模式时用，TUI 模式时为 nil
}

func NewEventBus(bufferSize int) *EventBus {
    return &EventBus{
        ch:   make(chan RenderEvent, bufferSize),
        done: make(chan struct{}),
    }
}

// Emit 非阻塞发送（channel 满时丢弃，避免阻塞 agent 推理）
func (eb *EventBus) Emit(evt RenderEvent) {
    select {
    case eb.ch <- evt:
    default: // drop on full
    }
}

// Events 返回只读 channel，供渲染层消费
func (eb *EventBus) Events() <-chan RenderEvent {
    return eb.ch
}

// Shutdown 发送关闭信号
func (eb *EventBus) Shutdown() {
    close(eb.ch)
}

渲染层（TUI 模式）

// tui/renderer.go

func StartRenderer(bus *output.EventBus, app *tview.Application, msgView *tview.TextView, ...) {
    go func() {
        for evt := range bus.Events() {
            switch evt.Type {
            case output.EvtMessageChunk:
                app.QueueUpdateDraw(func() {
                    fmt.Fprint(msgView, evt.Content)
                    msgView.ScrollToEnd()
                })
            case output.EvtReasoningStart:
                app.QueueUpdateDraw(func() {
                    fmt.Fprint(msgView, pretty.TReasoningStart())
                })
            case output.EvtToolCall:
                app.QueueUpdateDraw(func() {
                    fmt.Fprint(msgView, pretty.TToolCall(evt.Content)+pretty.TToolArgs(evt.Args))
                })
            // ... 其余事件类型
            case output.EvtShutdown:
                return
            }
        }
    }()
}

一个问题需要你判断

Widget 操作（SetFocus、SetDisabled、SetInputCapture）是同步命令式的，不适合用 channel 事件。比如 InputArea 的 SetInputCapture 注册键盘回调——这东西没法 emit 成一个事件。

A

Widget 操作另走一个小接口

输出类事件走 EventBus，widget 操作（Focus/Disabled/Capture）定义一个 WidgetOps 接口（~5个方法），和 EventBus 一起注入

B

Widget 操作也走 channel，渲染层通过回调通道回传结果

全异步，但需要双向通道，实现复杂。SetInputCapture 这类回调注册比较别扭

C

Widget 操作暂时不动

只把消息输出（EvtMessageChunk ~ EvtShutdown）走 EventBus，widget 操作保持 global 引用。后续如果有 CLI 模式需求再说
