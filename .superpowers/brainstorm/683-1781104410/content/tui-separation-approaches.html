TUI 分离：三种轻量方案

目标：抽离 TUI 渲染，不重构其余结构

当前 TUI 调用分布

handler/runIteratively.go → global.Print2AgentMessageView() [提示语]
                          → global.Sidebar, InputArea, StatusBar [widget操作]
                          → global.App_p.SetInputCapture() [键盘监听]
handler/runOnce.go        → global.Print2AgentMessageView() [错误信息]
                          → tip.StatusBarScrollingTip(...) [状态栏动画]
handler/message.go        → global.Print2AgentMessageView() [正文/工具/推理渲染]
session/summarizer.go      → fmt.Fprint(global.AgentMessage, ...) [摘要展示]
bootstrap/Initializer.go  → global.Print2LogView() [初始化日志]
                          → ShowErrorAndExit / ShowSuccessAndExit [弹窗提示]
bootstrap/Bootstrap.go    → global.AgentMessage [退出消息]
                          → global.App_p [应用生命周期]

三种方案

A

接口注入 — OutputBus

新建 output/ 包，定义 OutputBus 接口，包含 PrintMessage、PrintToolCall、PrintReasoning、ShowError 等方法。global.AgentRunner_p 上加一个 OutputBus 字段，初始化时注入 TUI 实现（或 CLI 实现）。

Pros

  • 改动最小，只改渲染调用点
  • 接口清晰，易测试
  • 保留了切换到 CLI 的可能

Cons

  • widget 操作（InputArea, StatusBar）难以接口化
  • global 包仍然存在
B

事件通道 — EventBus

用 Go channel 传递 RenderEvent 结构体。业务逻辑 emit 事件，TUI 层单独 goroutine 消费并渲染。完全异步，生产和消费彻底解耦。

Pros

  • 完全异步，不阻塞业务逻辑
  • 生产和消费彻底解耦
  • 可以轻松添加日志/监控中间件

Cons

  • 需要处理 channel 生命周期
  • 异步调试复杂
  • 对现有同步渲染逻辑改动较大（当前用 QueueUpdateDraw 已经是同步语义）
C

最小手术 — 只抽消息渲染

不动 global 包，不引入新接口。只把 handler/message.go 的 printMessage 函数改为接受一个 io.Writer 参数，其余 TUI 调用（widget操作、Sidebar等）保持原样。

Pros

  • 改动范围极小（~50行）
  • 风险最低
  • 消息渲染可测试

Cons

  • 只解决了消息渲染，widget操作仍耦合
  • CLI模式需要更多后续工作
  • 分离不彻底
